## 1. O252: other directories' lines after a write

### The overlays

`withoutDir` (`libraries.ts:90-116`), `withMovedDir` (381-407) and
`withLibraryMade` (182-207) change only the written directory's own copies.
Each also rewrites, in every directory, the `nested` and `inside` line whose
path is the written directory's, as `withoutLibrary` (125-145) and
`withLibraryRenamed` (152-176) already do by name:

| Write | The written path's line in other directories |
|---|---|
| unlink from library L | drops L's name; a line left with no name goes |
| removal (`'removed'`) | the line goes |
| move from L to T | T's name in place of L's |
| New library made over the path | adds the new library's name |

Lines name their holders ascending by library id (`libraries.ts:48-60`,
210-219). The rewrite keeps that order. Check whether a new library's id is
always the largest before relying on it; if it is not, sort by the id the
make's answer carries.

The list is still read again after every one of these writes (`Libraries.tsx`
250-256, 307, 378). The overlay is what the page draws until that read lands, or
after it fails.

### Refusals that reach the page

- `MoveRoot.tsx` (refusals 184-215) and `RemoveRoot.tsx` (`confirm`, 150-163)
  hand a 409 to the page as `UnlinkRoot` does: `onRefused(sentence, status)` →
  RootRow's `onHeldRefusal` (`RootRow.tsx:1139-1148`), so the page asks for the
  scan status again.
- `RemoveLibrary.tsx` (its dry run and `confirm`) hands a 409 to `LibraryPage`
  the same way: `onRefused(sentence, status)` → `heldRefusal`, which reads the
  library's scan status again through the store (`readNow(libraryScan(…))`).
  An answer in new words reaches `taken`, which sets `removalHeld` (Remove…
  held under its O250 words, and the held poll reading until the hold ends)
  or takes up a scan of the library it finds running. Once the read is
  answered, `heldRefusal` also sets `removalHeld` from the newest answer the
  store holds, since an answer in words the store already holds never reaches
  `taken`: a hold the page gave up after failed reads is drawn again, and an
  answer a newer read overtook cannot hold Remove… over that read's.
- A 409 from the directory's own scan makes RootRow read its own status once
  (`scanStatus` → `absorb`, `RootRow.tsx:587-611`). RootRow then takes up the
  running scan and holds its buttons with "Scanning…". Today `useOtherScan`
  (`DirPage.tsx:138-151`) counts the own scan only beside a sibling's, so this
  refusal holds nothing.

### "No such …" (decision 3)

- `LibraryAt` (`Libraries.tsx:755-759`): "There is no library at this address:
  it may have been removed, or the libraries list on this page is out of date;
  reload the page to read it again."
- `DirAt` (787-792): "This library has no directory at this address: it may
  have been removed, moved to another library, or removed from this library, or
  the libraries list on this page is out of date; reload the page to read it
  again."

These cover a move whose list read failed, and a move into a library the move
itself made, whose Also in link opens `LibraryAt` before the list names it.

## 2. O250: why a button is held

Holds today, none drawing words:

- **Library page, Remove…** is held by `removalHeld` (`held_removals`,
  `LibraryPage.tsx:611`, 689, 1412) while a scan around or inside one of its
  directories runs that the library does not walk. The scan lines draw only
  while `running` (1216, 1222).
- **Directory page, Remove…** is held by `removalHeld` (`useOtherScan`,
  `DirPage.tsx:99-203`; `RootRow.tsx:1104`).
- **Directory page, Remove from <library>…** is held by
  `unlinkHeld = scanning || moveHeld` (`RootRow.tsx:819`, 1084).
- **Directory page, Move…** is held by `moveHeld` (936). `moves_held` is the job
  lock, so a scan of any library holds it.

What each draws while held by something other than its own scan (its own scan
already draws "Scanning…"):

| Button | Where | Words while held |
|---|---|---|
| Library page Remove… | its Removal row's help (`LibraryPage.tsx:1404`) | "Waits for a scan of a directory around or inside one of <library>'s directories." |
| Directory page Remove… | its row's help (`RootRow.tsx:1094-1098`, both branches) | "Waits for a scan of a directory around or inside this one." |
| Directory page Remove from <library>… | its row's help | "Waits for a scan or another library job to finish." |
| Directory page Move… | a muted line in RootRow's `notices` (`DirPage.tsx:288`), drawn as the scan lines are | "A scan or another library job is running; move this directory once it has finished." |

When the hold ends, each help goes back to its words of today.

- Each held button is described by its help (`aria-describedby`). `Row`
  (`settingsLayout.tsx:296-344`) gives ids only to a child that is a function,
  so it gains a way to describe a plain child, or these rows pass a function
  child.
- A help text that grows moves only the Removal rows below it. Removal is the
  last box on both pages.
- The pin at `LibraryPage.test.tsx:1713` (no line in this state) stays true:
  the words are in the help, not a `.scanning` line.

## 4. O255: the report line

The line belongs to `useLateAnswers` (`configPages.tsx:106-266`) and goes when
the next answer replaces it, at a change of page, or at `made`. These also clear
a line drawn on the library page:

- **An add:** wrap `onAdded` in `Libraries.tsx` (`remember`, 312-327, 638).
- **A rename:** `follow` (`configPages.tsx:185-198`; `Libraries.tsx:510`) stops
  carrying the line to the new address.
- **A Scan library press:** LibraryPage tells the screen through a new `onScan`
  prop (`LibraryPage.tsx:962`).

Users shares the hook but writes nothing where its line is drawn
(`Users.tsx:206-216`), so the change lives in `Libraries.tsx`, not in the hook.

## 5. O256: the Remove dialogs

`RemoveRoot.tsx:207-212`'s last paragraph becomes:

> Nothing here can be undone from this screen. What goes is everything derived
> from files no other directory holds, and everything anybody recorded against a
> work that goes. No archive on disk is changed. A work that stays takes its
> documents under .taiyaku/ to the directory that now holds its files, if that
> directory keeps documents; the report after the removal lists any left behind
> as orphaned documents.

`RemoveLibrary.tsx:209-214` is the same with "files no other library's
directories hold".

What the server does (`crates/taiyaku-library/src/scan.rs:1498-1537`,
`carry_documents`): a carried document is renamed through `hand::rename_from`,
which moves it only where the receiving root keeps documents. A document left
in a `.taiyaku` no root holds is answered for the report. One left under a live
root's `.taiyaku` is not listed, because that root's `reconcile` reports it.

**Check before the words ship:** that the report each dialog draws after a
removal shows these left documents, so "the report after the removal lists any
left behind as orphaned documents" is true on screen.
