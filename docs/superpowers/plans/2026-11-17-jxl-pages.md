# Reading JPEG XL pages (O130) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An archive or folder of `.jxl` pages reads like any other: counted at scan, also where main stored it uncounted, without hashing anything again; decoded wherever taiyaku decodes; sent as stored to a client whose `Accept` names `image/jxl` and as a JPEG made once and cached to every other. Closes O130.

**Architecture:** `taiyaku-read` counts `jxl` entries as pages and names a per-format *reader signature*. The store keeps, per `scan_entry` row, the signature its count was taken under, and a scan re-counts a file whose signature moved, keeping its digest. `taiyaku-serve` registers one JPEG XL decoder with `image`'s hooks, so every decode site (covers, tiles, resized pages, the CLI) reads JPEG XL. The page routes choose a variant from the request's `Accept`: the stored bytes, or for a JPEG XL page a JPEG made once (the original JPEG rebuilt where the file holds one), each with its own `ETag` and `Vary: Accept`. Covers are always the JPEG variant.

**Tech Stack:** Rust: `image` 0.25.9 with a decoder registered through `image::hooks` (`jxl-oxide` 0.12.6 or `jxl` 0.8.0, chosen by Task 1); zip 9.1.3; rusqlite on SQLite 3.53 here and 3.40.1 in CI and the image; axum. `cjxl`/`djxl` 0.12, `magick`, `cjpeg` on the dev machine for fixtures. No web code.

**Spec:** `docs/superpowers/specs/2026-11-17-jxl-pages-design.md` (approved by the owner).

**O-numbers:** closes O130. **This branch claims O390, O349, O350 and O388.** Claimed elsewhere: O336 and O341 (paused-frozen), O337 (resize-polish), rows from O342 (content-fingerprints' plan, so O342–O344 are left to it), and O345–O347 (rar-libarchive's PR 1 plan). O390 is opened by Task 10 (Decision 11); O349–O350 are for findings during the build, and any unused one is released in the What's next memory. At the final rebase, renumber to the next free number above main and above every claim recorded for an unmerged branch (memory `taiyaku-open-items-ritual`, last paragraph).

## Decisions this plan makes

The spec leaves these to the builder ("Left to the builder") or reads two ways; each is decided here so no task has to.

1. **The registration lives in `taiyaku-serve`**, as `pub mod jxl`: content-fingerprints moves the shared decode code there (its plan: `taiyaku_serve::fingerprint`, no new crate), and the CLI already depends on serve. `register()` is idempotent (`std::sync::Once`) and is called at the top of the CLI's `main()` and of `taiyaku_serve::serve()`; tests that decode JPEG XL call it themselves.
2. **One production decode site bypasses the hooks.** The CLI's `report::prepare` (behind `verify`) uses `image::load_from_memory`, which guesses formats without hooks and decodes without limits. It moves to the hooked, limited decode. `cover.rs`'s `fits_within` and `decode_limited`, the CLI's `decode_luma` and `match_experiment/sheet.rs` already go through `ImageReader::with_guessed_format`.
3. **The variant comes from the request, not the page.** `serve_page` and `stream_page` answer a matching `If-None-Match` before the page is read, so the tag cannot depend on whether the page is JPEG XL. A request that does not name JPEG XL gets JPEG-variant tags on every page. The cost: after the upgrade, each page such a client had cached is fetched once more, and every library cover's `v=` changes once, because a cover of a JPEG XL page that fits its size is the JPEG made here and its version must name that rendering (O106, O224).
4. **A library cover is always the JPEG variant, with no `Vary`**: its address is kept for good (`COVER_CACHE_CONTROL`), so it cannot vary. Only JPEG XL is converted: a PNG page 0 that fits keeps O133's behaviour (the page's own bytes). The spec's "covers are always JPEG" is read as "never JPEG XL". OPDS covers and tiles always decode, so they are JPEG already.
5. **The signature is kept per entry** (`scan_entry.counted_by`), not per store or per directory. Scans run one directory at a time, and a nested directory takes rows from the one around it (`copy_entry`), so one stored value would be set by the first directory scanned and skip the rest. Per entry also lets the RAR work re-count RAR rows alone, as its design asks.
6. **Which entries re-count:** a *file* whose stored `counted_by` differs from `reader_signature(format)`. Folders never: the walk counts a folder's pages on every scan (`measure_dir`, and `record`'s unchanged branch rewrites a directory's total), so for folders the spec's "counted once more" already happens. A re-count writes `format`, `pages`, `title` and `counted_by`; it keeps `size`, `mtime` and `sha256`, and it is not counted in `ScanReport::updated`. Not migration 024's `mtime = -1`: that empties `sha256`, so the derive would hash every archive in the library again.
7. **Decoder limits:** the hook's decoder honours `image::Limits` through `set_limits`: `max_image_width`/`height` before decoding, and `max_alloc` over its own working memory, not only over the output buffer `ImageReader::decode` reserves first.
8. **Lossy tolerance** against `djxl`: Task 1 sets it from the winner's measured differences on the fixtures, at most 4 levels (8-bit) per channel. Lossless and grey fixtures are bit-exact.
9. **"One past the decode limits"** is a fixture past the limits its test sets (Decision 7's tests). A fixture past the server's 3 GiB ceiling would need an input over 3 GiB to make.
10. **The JPEG of a JPEG XL page** is encoded at quality 90 (screentone and thin ink survive it; a full page is what a reader looks at), and transparent ground is flattened onto white (a page's ground is paper). Covers and tiles keep `encode_jpeg` as it is.
11. **Mixed entries.** The spec accepts that an entry holding JPEG and JPEG XL pages renumbers when JPEG XL starts counting. The same renumbering leaves that entry's cached renderings and its tags, keyed by digest and offset, naming the old pages until its file changes: a zip's digest is its bytes, so nothing re-keys them (a folder's digest goes stale as O56 describes). Accepted under the same ruling and filed as O390, with no code.
12. **The O90 test** `an_archive_of_pages_taiyaku_does_not_read_is_named_as_uncounted` uses `.jxl` as its unread page type. It moves to `.heic`, so O90's coverage of `Unreadable::uncounted` stays.
13. **If paused-frozen has merged before Task 8**, the re-count branch fills the held reading where the count changes and the row has a digest, as that branch's moved-entry branch does, so a frozen derive keeps reading the count its work was written from.

## Review Focus

1. **A JPEG XL page with transparency, sent to a client that does not name JPEG XL:** the transparent ground comes out white, not black. Task 5 (d).
2. **A JPEG XL entry that is corrupt or cut short, asked for by such a client:** the route gives the refusal `routes::unreadable` gives any unreadable page, and leaves no cache file. Task 6 (j).
3. **A cut-short JPEG left in the cache (O105's shape):** read as a miss and made again, never served. Task 5 (c).
4. **A scan cancelled while re-counts are due:** nothing is written, and the next scan re-counts them. Task 8 (f).
5. **Accept headers as clients send them:** absent, `image/*` alone, `image/jxl;q=0`, `IMAGE/JXL`, `image/jxl` on a second `Accept` line, and Panels' spaced list. Task 6 (a).

### As built

*The plan above is kept as written and superseded here, per this project's convention. What shipped differs from it in twelve places:*

- **The decoder is jxl-oxide 0.12.6** (`features = ["image"]`, MIT OR Apache-2.0). `jxl` 0.8.0 failed Decision 7, since its `set_limits` counts only the output buffer, and declares `rust-version` 1.89. jxl-oxide reports a decode that outgrew `max_alloc` as a decoding error ending in `jxl_grid::OutOfMemory`, so `jxl.rs` maps it to `ImageError::Limits`; `jxl-grid`, and for the metadata cap below `jxl-bitstream`, `jxl-oxide-common` and `brotli-decompressor`, are named directly in `taiyaku-serve`, each at the version jxl-oxide already resolves. The lossy tolerance is 1 level.
- **The migration is 029**, `029_entry_counted_by.sql`: paused-frozen took 027 and merged before Task 8, and content fingerprints took 028 and merged before this branch, so Decision 13 applies, and a re-count that changes a file's count holds the reading it replaces.
- **A page cut short is never decoded in part.** jxl-oxide renders what it has of a frame not fully read, so the decoder first checks that the first frame is whole; where the server has to decode such a page, it gets the refusal any unreadable page gets and leaves no cache file. A client that names `image/jxl` is sent the stored bytes as they are.
- **Metadata boxes are capped** (`METADATA_CAP`, 16 MiB): `brob` boxes and a `jbrd` box's compressed stream, together, are measured before jxl-oxide inflates them, which it does outside `max_alloc`, where the server has to decode the page; a page sent as stored at full size is not decoded, so the cap does not reach it. An embedded ICC profile is not capped, and is O350.
- **A re-count whose read fails, on a file that had a count, keeps the row as it was**, count and signature, and is tried again at the next scan.
- **A rebuilt JPEG is used only when it would pass the cache's own check** (`whole_jpeg`); otherwise the page is decoded and encoded, so the cache never holds a file it would refuse.
- **Every JPEG the server encodes from an image with alpha is laid on white**, of any format, covers and tiles included (`cover::onto_white`). Decision 10's "covers and tiles keep `encode_jpeg` as it is" is superseded for alpha only, and no format version moved.
- **Desktop Chrome 157 names `image/jxl`** (Task 9), so it is sent JPEG XL pages as stored at full size. `CHROME_ACCEPT`, from Chrome 154, stays in the tests as a client that does not name it.
- **Task 10 opened O349 and O350 as well as O390**: O349 from Task 9's memory reading, O350 from the whole-branch review. O388 came from the review of the fix round.
- **The workspace declares Rust 1.91 since #265**, so the decoder is checked at 1.91, not the 1.88 this plan names.
- **A folder whose page count moved has its digest taken again.** The goal's "without hashing anything again", Decision 6's "Folders never" and Decision 11's "a folder's digest goes stale as O56 describes" do not hold for it. A folder that holds a digest, was listed whole and is walked at another page count than it stored takes the path a changed folder takes (`scan::Held::digest_outdated_by`), because no read of it could hash to the old digest. A folder holding JPEG and JPEG XL pages is hashed once at the first scan after the upgrade, and its renderings and page tags get new keys. A directory newly nested over such a folder gives its digest up the same way as its walk takes the row over (`scan::carry_reading`). A zip keeps its digest, so O390 stands for zips alone. A saved place keeps its slot in both.
- **A decode on a lowered thread renders on that thread** (`jxl::render_pool`, `priority::thread_is_lowered`) and leaves rayon's shared pool to other decodes, because that pool's threads keep the priority of the thread that first used it.
