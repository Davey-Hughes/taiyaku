# mimalloc as the server's allocator (O349) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The `taiyaku` binary allocates through mimalloc, so memory freed after a burst of JPEG XL decodes goes back to the system. It ships only if a measured run against main meets the spec's three-part criterion, and only then does O349 close.

**Architecture:** One dependency (`mimalloc` 0.1.52, default features) and a `#[global_allocator]` static in `crates/taiyaku-cli/src/main.rs`; a CLI test proves the built binary starts mimalloc. A scripted run of release builds of main and of the branch, two each in the order main, branch, branch, main, decides whether it ships. If it does, the open-items ritual closes O349.

**Tech Stack:** Rust 1.100.0 (pinned; floor 1.91), mimalloc 0.1.52 → libmimalloc-sys 0.1.49 (mimalloc's C v3.3.2, compiled by `cc`), cargo-nextest, curl, `/proc/<pid>/status`.

## Global Constraints

- `mimalloc = "0.1.52"` in `crates/taiyaku-cli/Cargo.toml`, default features only (its default is mimalloc's C v3.3.2; the `v2`, `override`, `secure` and other features stay off). No mimalloc option is set in code, the Dockerfile or the server's environment; `MIMALLOC_VERBOSE=1` appears only in the test and the checks below.
- `#[global_allocator]` only in `crates/taiyaku-cli/src/main.rs`. No library crate changes, so their tests keep the system allocator. (The cli crate's own unit tests compile with `main.rs` and so run under mimalloc; that is intended.)
- No `malloc_trim`, `mallopt` or `MALLOC_ARENA_MAX`; no change to `cover::GENERATION_LIMIT`, `jxl::render_pool` or the fingerprint pass's workers.
- `unsafe_code = "forbid"` stays. The static needs no `unsafe`: a probe crate with `forbid(unsafe_code)` and this static built on 1.100.0 with mimalloc 0.1.52 while this plan was written.
- `deny.toml` is not edited: it configures the advisories check only and no licence check, so there is no allow-list for MIT to be added to.
- Code comments say why only: no figures, dates or history (`scripts/check-comments.mjs`).
- Shell is zsh: no `cd` (use `git -C`, `env -C` and absolute paths); `>` is noclobber, so write with `>|`; `grep` is a function that skips binary files, so use `rg` or `grep -a`; time with `date +%s.%N` (no `/usr/bin/time`).
- Servers listen on `127.0.0.1:4417` only (never 4399). Kill by PID after reading `/proc/<pid>/exe`, never by pattern; never restart a server outside the Task 2 driver; after every kill, `ss -lptn 'sport = :4417'` lists nothing.
- Another branch is built on this machine. The gate, the image build and the whole measurement run under `flock /run/user/1000/taiyaku-gate.lock`, and each starts only once `pgrep -x cargo-mutants` finds nothing.
- **The gate**, wherever a step says "run the gate as `<name>`":
  `env -C $W -u TAIYAKU_CORPUS RUST_TEST_THREADS=8 NEXTEST_TEST_THREADS=8 flock /run/user/1000/taiyaku-gate.lock scripts/check-all.sh >| $EV/<name>.log 2>&1; echo "exit=$?" >| $EV/<name>.exit`
  then `rg -a -n 'all green|NOT MEASURED|^error' $EV/<name>.log`, and quote the "all green" line in the report. Never pipe the gate itself. The only acceptable NOT MEASURED item is the corpus checks (no `TAIYAKU_CORPUS`).
- Every hand-applied defect is restored afterwards and `git -C $W status --short` is checked against what the task changed.

## Review Focus

1. **The image.** mimalloc's C is compiled by bookworm's gcc in `rust:1-bookworm` and run on `debian:bookworm-slim`; CI builds the image only on `main`, after the merge, and main's CI deploys to the NAS. Task 1 Step 8 builds the real Dockerfile and runs its binary before the merge.
2. **A free across the Rust/C boundary.** With mimalloc for Rust and glibc for C, C freeing a Rust allocation, or Rust freeing a C one, corrupts the heap where it used to work by accident. Task 1 Step 6 reads every such site in the dependencies that link C.
3. **A server idle after the burst.** mimalloc gives freed memory back as later allocator calls run; a server with no traffic after the burst may keep it. Only the measurement can show this: Task 2 reads at 30 s and 5 minutes with no request between.
4. **The wrong binary in a slot** would invert the verdict. Task 2 Step 2 checks that each copied binary does (branch) or does not (main) start mimalloc.
5. **A baseline that does not reproduce O349** would let the criterion pass while showing nothing. Task 2 Step 6 stops if main gives its memory back on its own.

- [ ] **Step 1: Write the failing test** in `crates/taiyaku-cli/tests/cli.rs`, using the file's `taiyaku()` helper. Its doc comment says why: the binary allocates through mimalloc, which gives memory freed after a burst back to the system (O349), and `MIMALLOC_VERBOSE` makes mimalloc say so on stderr as it starts.

```rust
#[test]
fn the_binary_allocates_through_mimalloc() {
    let run = taiyaku()
        .env("MIMALLOC_VERBOSE", "1")
        .output()
        .expect("the binary runs");

    assert_eq!(run.status.code(), Some(0));
    let stderr = String::from_utf8_lossy(&run.stderr);
    assert!(
        stderr.contains("mimalloc: process init"),
        "mimalloc starts in the binary: {stderr}"
    );
}
```

The string was read while planning: in a probe binary with mimalloc 0.1.52 as its global allocator, `MIMALLOC_VERBOSE=1` printed `mimalloc: process init: 0x…` then `v3.3.2 (built on …)` to stderr only; with the static removed and the dependency kept it printed nothing.
