# M5b — The module system and six modules Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every reading behaviour the reader offers becomes an individually switchable, tunable module — and the fast flick stops flickering.

**Architecture:** One declarative `ReaderModule` contract, six modules built against it, and the settings panel generated from each module's own defaults rather than hand-written per module. The contract is proven by having six implementations, not one. Two Rust additions ride along because a module needs them: `Edition::chapter_at` for the chapter readout, and an `ETag` on page responses so `prefetch` can measure what O1 has been deferred on.

**Tech Stack:** Rust 2024, `wasm-bindgen`; React 19 + Vite + TypeScript + Vitest.

**Amended after Task 2:** Task 11 originally owned building the registry in `App.tsx` and dispatching module keys through `keys.ts`, alongside the settings panel. A review found `buildRegistry` had zero production callers at that point — `directionModule` was declared against the contract but never passed to it, so the startup collision check and the duplicate-id check, the entire justification for the contract being declarative, never ran, and Task 2's own `d` handling was hand-wired rather than dispatched. Leaving that wiring in Task 11 meant Tasks 3, 4, 7 and 9 would each build a module against a contract nothing had proven was connected to anything, and each would hand-wire its own key exactly as Task 2 did, needing unpicking later. The registry is now built at startup and module keys dispatch through `keys.ts`'s `intentOf` as of the commit before Task 3, while exactly one module and one key existed to move — the cheapest point to have fixed it. Task 11, below, is scoped to the settings panel and closing the milestone only.

## Global Constraints

- **Nothing Vitest loads may import `web/src/resolver.ts` as a value**, directly or transitively. `crates/taiyaku-wasm/pkg/` is gitignored, so a fresh CI clone leaves a dangling symlink for the `file:` dependency. `App.tsx` legitimately value-imports it and no test reaches `App.tsx`. Type-only imports are erased and are fine.
- **`pageUrl`/`thumbUrl` take a PAGE index, not a SLOT index.** They diverge from the first joined spread onward and coincide only at index 0. A caller holding a slot converts via `Resolver.slotAt(edition, slot).page` first.
- **`Chrome`'s `displaySlot` is 1-based; every other value is zero-based** — `ReadingState.slot`, `Resolver.slotAt`, stored progress, and the server's range check. A display value must never reach storage, a URL, or the server.
- **`App.tsx`'s progress-write effect must keep depending on `session?.state.authority` and `session?.state.slot` and NOT on `session`.** That dependency array *is* the enforcement that a swap never writes progress; adding `session` would write on every swap and restore the drift bug with every test green. It carries an `oxlint-disable` block saying so. Do not remove it.
- **Never crop, distort or force-fill a page.** Fit whole, aspect preserved, downscale only, no upscale past 100%. Tiles included.
- **A slot is the addressed unit, never a page.**
- **`taiyaku-core` must keep building for `wasm32-unknown-unknown`, and must never take `wasm-bindgen`.** The binding lives in `taiyaku-wasm`.
- **No new Rust dependencies.** The set is `image`, `zip`, `sha2`, `rayon`, `base64`, `serde`, plus `axum`, `tokio`, `tower`, `ureq` in the server and `wasm-bindgen` in the binding.
- **No new npm runtime dependencies.** A dev-only dependency needs a stated reason.
- **CI:** `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test --workspace`, a wasm32 build, and a `web` job running `npm ci`, `lint` (`oxlint --deny-warnings`), `typecheck` (`tsc -b`) and `test`. **No CI job may use a JavaScript action** — the container has no node for one.

## What this plan deliberately does not do

- **Annotations** (M5c) and **the correction UI with O13** (M5d).
- **The `fit` and `filters` modules.** Specified in the design, and the contract this plan builds is what they slot into. `fit` is where the small-image fixture for the no-upscale rule belongs.
- **Position tracking in continuous-scroll mode.** Entering the mode scrolls to where you were; hand-scrolling still does not write the slot back. That wants an `IntersectionObserver` and is its own decision.
- **Closing O1.** This plan ships the validator and *measures*; whether O1 closes is what the measurement decides.

`web/src/module.ts`:

```typescript
/** A key a module claims, and the intent it produces. */
export interface KeyBinding {
  key: string
  intent: string
}

/**
 * A reader behaviour that can be switched off and tuned.
 *
 * Declarative rather than self-registering, and that is the whole design. A
 * module that registers itself on load cannot be enumerated while it is
 * disabled, so the settings panel would need hand-written knowledge of every
 * module — which is precisely the coupling "modular" exists to remove.
 * Declaring also turns a keybinding collision into a startup error instead of
 * two modules silently fighting over one key.
 *
 * A module uses the extension points it needs and no others.
 */
export interface ReaderModule<P> {
  id: string
  label: string
  /** The preference slice and its defaults. The settings panel is generated from this. */
  defaults: P
  /** Keys this module claims while enabled. Checked for collisions at startup. */
  keys?: KeyBinding[]
}

export interface Collision {
  key: string
  modules: string[]
}

/**
 * Keys claimed by more than one module.
 *
 * A module claiming the same key twice is not a collision — that is one
 * module's own arrangement and nothing else can be surprised by it.
 */
export function collisions(modules: ReaderModule<unknown>[]): Collision[] {
  const claims = new Map<string, string[]>()
  for (const m of modules) {
    for (const key of new Set((m.keys ?? []).map((k) => k.key))) {
      claims.set(key, [...(claims.get(key) ?? []), m.id])
    }
  }
  return [...claims.entries()]
    .filter(([, ids]) => ids.length > 1)
    .map(([key, modules]) => ({ key, modules }))
}

export interface Registry {
  ids: string[]
  get(id: string): ReaderModule<unknown> | undefined
  all(): ReaderModule<unknown>[]
}

/** Build the registry, refusing at startup if two modules claim one key. */
export function buildRegistry(modules: ReaderModule<unknown>[]): Registry {
  const clashes = collisions(modules)
  if (clashes.length > 0) {
    const detail = clashes.map((c) => `\`${c.key}\` claimed by ${c.modules.join(' and ')}`)
    throw new Error(`two modules claim one key: ${detail.join('; ')}`)
  }
  const byId = new Map(modules.map((m) => [m.id, m]))
  return {
    ids: modules.map((m) => m.id),
    get: (id) => byId.get(id),
    all: () => modules,
  }
}
```

`web/src/prefs.ts`:

```typescript
/**
 * Module preferences, stored client-side.
 *
 * The design's rule: position and content are server-side because they must
 * survive a different machine; layout and preference are client-side, which is
 * the precedent parity breaks set. A module toggle, an animation duration and a
 * reading-direction override are all preferences about the person, not facts
 * about the work.
 *
 * A stored slice is merged over the defaults rather than replacing them, so a
 * module gaining a setting does not strand every reader who saved before it
 * existed. Unparseable storage falls back to the defaults: a reader whose
 * preferences are corrupt should get a working reader, not a blank page.
 */
const key = (id: string) => `taiyaku.prefs.${id}`

export function loadPrefs<P extends object>(id: string, defaults: P): P {
  try {
    const raw = localStorage.getItem(key(id))
    if (raw === null) return { ...defaults }
    const stored = JSON.parse(raw) as Partial<P>
    return { ...defaults, ...stored }
  } catch {
    return { ...defaults }
  }
}

export function savePrefs<P extends object>(id: string, prefs: P): void {
  try {
    localStorage.setItem(key(id), JSON.stringify(prefs))
  } catch {
    // A full or unavailable store must not break reading. The preference is
    // lost on reload, which is visible and recoverable; a thrown error here
    // would unmount the reader mid-page.
  }
}

export function resetPrefs(id: string): void {
  try {
    localStorage.removeItem(key(id))
  } catch {
    // Same reasoning as `savePrefs`.
  }
}
```

import type { ReaderModule } from '../module'

export type Direction = 'rtl' | 'ltr'

/** Overrides are per edition, because editions of one work can differ. */
export interface DirectionPrefs {
  override: Record<string, Direction>
}

/**
 * Which way the pages read.
 *
 * `work.reading` in the sidecar is a fact about the work and is never written
 * back to. An override is a preference about the person reading it, so it lives
 * client-side with the other preferences.
 */
export function effectiveDirection(sidecar: Direction, override: Direction | undefined): Direction {
  return override ?? sidecar
}

export const directionModule: ReaderModule<DirectionPrefs> = {
  id: 'direction',
  label: 'Reading direction',
  defaults: { override: {} },
  keys: [{ key: 'd', intent: 'direction:toggle' }],
}

import type { CSSProperties } from 'react'
import type { ReaderModule } from '../module'

export interface MotionPrefs {
  animate: boolean
  ms: number
}

/**
 * The page transition, or nothing.
 *
 * Returns an empty object rather than `transition: 'none'` when there is
 * nothing to animate. An inline `none` would beat a `prefers-reduced-motion`
 * rule in the stylesheet; declaring nothing lets the reader's own OS setting
 * govern, which is the polite default and costs nothing.
 */
export function transitionStyle(prefs: MotionPrefs): CSSProperties {
  if (!prefs.animate || prefs.ms <= 0) return {}
  return { transition: `opacity ${prefs.ms}ms ease` }
}

export const motionModule: ReaderModule<MotionPrefs> = {
  id: 'motion',
  label: 'Motion',
  defaults: { animate: true, ms: 120 },
}
```

**Interfaces:**
- Consumes: `groups(slots, mode, reading)` from `pairing.ts`.
- Produces: `regroupModule`, `toggleBreak(breaks, slot)`; and `groups` gains a `breaks` parameter.

Two-page mode pairs slots `(0,1), (2,3), …`. A joined spread already interrupts that — M5a handles the case the format makes derivable. **This task adds the case it does not:** one unpaired page throws the parity off for everything after it, and only a person can see that. A break at slot *k* restarts pairing there.

Breaks are **per edition**, because editions differ in which pages are missing, and are **stored client-side** — the sidecar describes correspondence; pairing parity is layout, varies by reading mode, and would be noise in a file meant to diff meaningfully in git.

import type { ReaderModule } from '../module'

export interface RegroupPrefs {
  /** Break positions per edition key. */
  breaks: Record<string, number[]>
}

/**
 * Insert or remove a parity break at a slot.
 *
 * Kept sorted so the same set of breaks always produces the same layout,
 * whatever order a reader inserted them in. A break at slot 0 is refused
 * because pairing already restarts there — accepting it would store a
 * preference that cannot change anything.
 */
export function toggleBreak(breaks: number[], slot: number): number[] {
  if (slot <= 0) return breaks
  return breaks.includes(slot)
    ? breaks.filter((b) => b !== slot)
    : [...breaks, slot].sort((a, b) => a - b)
}

export const regroupModule: ReaderModule<RegroupPrefs> = {
  id: 'regroup',
  label: 'Regroup pages',
  defaults: { breaks: {} },
  keys: [{ key: 'b', intent: 'regroup:toggle' }],
}
```

```rust
/// Where a slot falls in a chapter-organised edition.
///
/// `path` is the member's path as the sidecar records it, offered as a label.
/// Nothing here parses it: a fan release's `c000.cbz` may or may not be chapter
/// zero, and inferring a chapter number from a filename is precisely what this
/// function exists to avoid — `notes.md` records two series where the declared
/// names are wrong and the content-derived answer is right.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ChapterAt {
    /// Zero-based index of the member within the chapter-organised edition.
    pub member: usize,
    /// How many members that edition has.
    pub of: usize,
    pub path: String,
}

impl Sidecar {
    /// Which chapter a slot of `from` falls in, or `None`.
    ///
    /// `None` covers three situations deliberately: this work has no
    /// chapter-organised edition (the common case, and not an error); there is
    /// no path from `from` to it; or this slot has no counterpart there.
    ///
    /// The chapter-organised edition is the one assembled from the most
    /// members. A work with two such editions is ambiguous, and the tie is
    /// broken by edition key so the answer is at least stable — if that case
    /// ever arises in practice it wants a real decision rather than this one.
    pub fn chapter_at(&self, from: &str, slot: Slot) -> Option<ChapterAt> {
        let (key, edition) = self
            .editions
            .iter()
            .filter(|(_, e)| e.members.len() > 1)
            .max_by(|a, b| a.1.members.len().cmp(&b.1.members.len()).then(b.0.cmp(a.0)))?;

        let landed = if key == from {
            slot
        } else {
            crate::route(self, from, key)?.resolve_slot(slot)?
        };
        let (member, _) = edition.locate(landed.page)?;
        Some(ChapterAt {
            member,
            of: edition.members.len(),
            path: edition.members[member].path.clone(),
        })
    }
}
```

**Spec coverage.** The spec's M5b row is "module system + `regroup`, `direction`, `motion`, `prefetch`, `readouts`, and `chapter_at` in the core" — Tasks 1, 4, 2, 3, 9, 7 and 5 respectively. Deliberately not covered, each named above: annotations (M5c), the correction UI and O13 (M5d), the `fit` and `filters` modules, and position tracking in scroll mode.

**Placeholder scan.** No "TBD", no "add error handling", no "similar to Task N". Four steps deliberately withhold code and require measurement instead — Task 5 Step 4, Task 9 Step 5, Task 11 Steps 2 and 3 — because the answer is a number nobody has yet, and writing an expected one is how M4's plan produced five defects.

**Type consistency.** `ReaderModule<P>` carries `defaults: P` in every module file. `Position { page, half? }` and `ReadingState { authority, slot, viewing }` are unchanged from M5a. `slot` is a flat zero-based index everywhere except `Chrome`'s `displaySlot`. `ChapterAt { member, of, path }` is the same shape in Rust, across the binding, and in TypeScript.

**Known weaknesses, stated rather than hidden.**

- **Task 5's chapter-edition rule is a heuristic.** "The edition with the most members" is right for every work in this corpus and is not a definition. A work with two chapter-organised editions gets a stable answer rather than a correct one, and the doc comment says so.
- **Task 9's decode test needs an injectable seam** to avoid a DOM library. If that shapes the component awkwardly, the implementer is told to say so rather than add the dependency quietly.
- **Task 10's memo adds interior mutability** to a type that currently has none. That is a real cost for a measured benefit that has not been measured yet — the count of route builds is the evidence, and it should be reported before the memo is called worthwhile.
