# O220 (an account can be left seeing no library): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Removing a library, removing its last folder or moving that folder
away goes through even when it is some account's only grant. The account is
then left seeing no library, never every library.

**Architecture:** An account's access stops being a list of folders where
empty means everything. It becomes `account::Access`, which is `Every` or
`Only(folders)`, and `Only` with no folders sees nothing. A stored
`user.every_library` column says which case an account is in. Once the
two-case type replaces `Principal.roots`, the compiler finds every reader.
The only-grant refusals, their triggers and O205's guard go. The dry runs name
the accounts a removal leaves with no library, the status says when an account
is restricted, and the web draws both.

**Tech Stack:** Rust 2024, rusqlite against the system SQLite, axum 0.8;
React 19, react-router, vitest, biome, pnpm.

## Decided while planning

These follow from the spec. They are listed for the user, and the plan is
written to them.

1. **A request with no `Principal` sees nothing.** The guard is attached to
   every guarded route (`routes.rs::build_router_serving`) and inserts a
   principal or refuses, so this only happens to a test calling a handler
   directly or after a routing mistake. `on_the_grant` answers it 401
   `unauthorized`, as `session.rs` does. `list_works` and `opds::granted()`
   read it as `Access::Only(vec![])`. `can_stream`'s and `can_download`'s
   "no principal means yes" are not grants and stay as they are.
2. **The dialogs name restricted non-admin accounts only.** An admin sees
   every library whatever its rows say, so an admin is not "left with no
   library" and is not named.
3. **Lifting the limit deletes the account's rows**, as choosing "Every
   library" does today. `{"every_library": false}` is refused with 400: it
   has no meaning that `{"libraries": [...]}` does not already carry.

### Task 1: `Access` replaces the folder list (no behaviour change for any stored account)

The compiler-driven half. After this task every reader takes `&Access`.
`access_for` still derives from the rows alone (no rows → `Every`), so no
stored account sees anything different. What is new is that `Only(vec![])`
sees nothing everywhere, and a request with no principal sees nothing.

**Files:** `account.rs`, `browse.rs`, `libraries.rs`, `auth.rs`, `session.rs`,

**Interfaces:**
- Produces, in `crates/taiyaku-library/src/account.rs`:

```rust
/// What an account may see, as the folders that hold it.
///
/// Two cases rather than a list where empty means "everything": a list that
/// can stand for every library turns any path that empties it (a revoke, a
/// removal, a folderless library) into a silent widening. `Only` with no
/// folders sees nothing. No `Default`, so each place that builds one says
/// which case it means.
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Access {
    /// An administrator, or an account set to "Every library", including any
    /// added later.
    Every,
    /// Only these folders (root ids).
    Only(Vec<i64>),
}

impl Access {
    /// Whether a folder is inside this access.
    pub fn allows(&self, root_id: i64) -> bool {
        match self {
            Access::Every => true,
            Access::Only(roots) => roots.contains(&root_id),
        }
    }
}
```

- `auth::Principal.access: Access` replaces `roots: Vec<i64>` (auth.rs:353).
  `from_account(account, access: Access)` sets `Access::Every` for an admin.
- `auth::access_of(extensions: &axum::http::Extensions) -> Access`: the

**Interfaces:**
- Consumes: `Access`, `access_for` (Task 1).
- Produces:
  - Migration 017, `SCHEMA_VERSION = 17`:

```sql
-- An account sees every library (1) or only those its user_library rows
-- name (0); 0 with no rows sees nothing. Without the column, an account with
-- no rows had to mean "every library", so emptying a grant widened it.
ALTER TABLE user ADD COLUMN every_library INTEGER NOT NULL DEFAULT 1
    CHECK (every_library IN (0, 1));
UPDATE user SET every_library = 0
    WHERE id IN (SELECT user_id FROM user_library);
-- Removing an account's only library no longer widens it, so nothing is
-- left for these to stop.
DROP TRIGGER only_grant_refuses_delete;
DROP TRIGGER only_grant_refuses_move;
```

  - `account::Grant { Every, Libraries(Vec<i64>) }` (library ids), and
    `Patch.grant: Option<Grant>` replacing `Patch.libraries` (account.rs:784).
    `Grant::Every` sets `every_library = 1` and deletes the rows;
    `Grant::Libraries(ids)` sets 0 and replaces the rows (an empty list is
    no library).
  - `access_for`: `every_library = 1` → `Every`; 0 → `Only(folders of the
    granted libraries)`, which is `Only(vec![])` with no rows. An admin is
    still `Every` in `from_account`.

    revoking the last grant leaves `Only(vec![])`.
  - `account::set_every_library(conn, user_id) -> rusqlite::Result<bool>`:
    `Grant::Every` for the CLI, `true` when it changed anything.
  - `browse::Status.restricted: bool`, true when the access is `Only`;
    `/api/library/status` sends `"restricted"` beside `"libraries"`.
  - `user_json` sends `"every_library": bool`. `PATCH /api/library/users/{id}`
